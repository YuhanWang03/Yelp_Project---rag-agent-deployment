🍽️ Yelp 商家智能问答 Agent

Yelp 评论问答：两个基线 + 四种智能体推理范式的对比，全部基于 DeepSeek-V4 · 2026 年 4 月 – 5 月

在线 Demo： huggingface.co/spaces/YUHAN03/yelp-rag-agent
技术栈： FAISS sentence-transformers LangGraph LangChain Gradio 5 DeepSeek-V4（Flash / Pro）
数据规模： 60,823 条评论 chunk · 50,000 条原始评论 · 160 家商家

1. 项目目标

在 Yelp 评论领域构建问答系统，并严肃地对比六种方法——两个基线 加四种智能体推理范式——回答：

  1. 推理结构重要吗？纯 LLM、固定 RAG 流水线，对比四种 Agent 范式 （ReAct、Plan-and-Solve、ReWOO、Reflection），在相同问题、工具和模型下比较。
  2. 显式 Reflection 或内置"thinking"有用吗？每种范式都在 DeepSeek-V4 thinking 开/关、Flash/Pro 两个模型上跑，同时测量质量和 成本/延迟。

2. 系统架构

用户问题
   │
   ├─► Direct LLM        ── 仅依赖参数化记忆（基线）
   ├─► RAG Baseline      ── Stats → FAISS 检索 → 结构化合成
   ├─► ReAct             ── 边推理边行动，自主调度工具
   ├─► Plan-and-Solve    ── 先规划全部工具调用 → 顺序执行 → solve
   ├─► ReWOO             ── 规划 → 并行执行 → solve
   └─► Reflection        ── 先答 → 自我批判 → 修正

四种范式共用相同的工具、检索和 DeepSeek-V4 后端，唯一变量是推理结构。

2.1 检索栈

  • Chunk 级 FAISS 索引（IndexFlatIP），共 60,823 条 chunk。 评论按 180 词、句边界感知地切分；embedding 经 L2 归一化， 使内积等价于余弦相似度。
  • 商家预过滤检索：维护 business_to_indices 映射， 直接在目标商家的 embedding 子集上算相似度，避免"全局 Top-K + 后过滤" 对低评论量商家失效的反模式。
  • Embedding 模型：sentence-transformers/all-MiniLM-L6-v2（384 维）。

2.2 后端抽象层（核心工程思路）

所有 pipeline 只依赖 BaseBackend 接口的一个方法 generate(prompt, temperature, max_tokens) -> str。 四个具体后端通过 YAML 配置即可互换：

后端用途调用端点
DeepSeekBackend 范式研究 + 在线 demo api.deepseek.com/v1
OllamaBackend 本地开发 localhost:11434
GroqBackend 备用 serverless api.groq.com/openai/v1
LMDeployBackend 自托管 OpenAI 兼容服务 OpenAI 兼容 HTTP

切换后端不需要改任何应用层代码 — 只需 CLI 参数 （--config configs/deepseek_v4_flash.yaml）或 HF Space 上的一条 secret。正是这层抽象让我们只用约 30 行就接入了 DeepSeek-V4，并把研究和在线 demo 都指向它。

3. 推理范式对比研究（DeepSeek-V4）

在原有三个系统之外，我们新增了三种智能体推理范式——Plan-and-Solve、ReWOO、Reflection，连同原有的 ReAct agent，在相同的 20 题上对比这四个范式（加 Direct LLM 和 RAG 基线）。每个范式跨两个 DeepSeek-V4 模型（Flash / Pro）和两种 thinking 模式跑，共 320 条答案，由 LLM-as-judge 在四个质量维度上评分（0–2 分/维度，满分 8）。效率（延迟/成本/token）取自原始运行指标。

范式说明：ReAct 边推理边行动，根据观测决定每一步；Plan-and-Solve 先规划全部工具调用再顺序执行；ReWOO 规划后并行执行；Reflection 先答、再自我批判与修正。框架（LangGraph）和工具保持不变，唯一变量是推理结构。

3.1 所有检索范式的质量都饱和

所有带检索的系统——RAG 基线和四个范式——都落在 7.8–8.0 / 8，统计上无法区分；只有无检索的 Direct LLM 崩到 0.2 / 8。在强模型 + 好检索下，推理结构不影响答案质量。

范式质量 /8延迟 (s)成本 ($)输入 tok输出 tok
Direct LLM0.23.80.0000755213
RAG Baseline7.83.20.00016577286
ReAct8.011.80.001186865765
Plan-and-Solve7.96.40.000402051433
ReWOO7.86.20.000362033404
Reflection7.910.80.000815540704

Flash，thinking off（Direct LLM / RAG 为参照基线）。

3.2 范式的取舍是效率，不是质量

把质量对延迟作图，结论一目了然：质量是贴近天花板的一条水平带，而延迟跨度超过 30×。ReAct 是 token 最贵的范式，因为它每轮都重发不断增长的消息历史（6865 输入 token，而 Plan-and-Solve 约 2051）。Plan-and-Solve 和 ReWOO 最精简；当计划含多个独立工具调用时，ReWOO 的并行执行略占优势。

3.3 thinking 税

DeepSeek-V4 的内置 thinking 模式带来约 4× 延迟、1.9× 成本，而质量变化仅 +0.00 / 8——即几乎为零。在质量已饱和的任务上，内部思考链买不来任何收益。

模型质量(off)质量(on)Δ 质量延迟成本
v4-flash7.887.95+0.073.0×1.5×
v4-pro7.937.93+0.003.9×1.9×

对 Plan-and-Solve、ReWOO、Reflection 取平均。

3.4 裁判验证（跨模型稳健性）

为排除自偏好偏差（V4 裁判给 V4 生成的答案打分），我们用另一个 模型族的独立裁判（OpenAI gpt-4o-mini）对全部 320 条答案重新 评分。两套裁判高度一致 — 行级 Pearson r = 0.97、 平均绝对差 0.11 / 8 — 且都把所有检索系统打到 天花板、把 Direct LLM 远远拉到底。范式对比的结论不依赖于裁判的 选择。

3.5 结论

在这个 RAG 问答任务上，范式选择是效率决策，不是质量决策。所有检索范式都达到天花板质量，所以正确选择是最便宜最快的：Flash 上的 Plan-and-Solve 或 ReWOO，thinking 关。显式 Reflection 不提升质量，却贵 2–3×；thinking 模式加大量延迟/成本、质量零增益——这回答了我们的出发问题：当质量饱和时，内置推理既不取代也不奖励显式 Reflection。Pro 的成本约为 Flash 的 10×，质量相同。

局限：0–2 量表在顶端太粗，难以区分接近天花板的答案（这是任务偏易的属性，不是裁判缺陷——见 §3.4）；未存检索 chunks，groundedness 按内部一致性评判。自偏好偏差已检验并排除（§3.4）。

5. 工程挑战与解决方案

5.1 DeepSeek-V4 thinking 模式的两个坑

接入 V4 的 thinking / 非 thinking 双模式时，发现两个会悄悄毁掉数据的 API 行为：

  • 共享 token 预算。thinking 模式下 max_tokens 是 推理链和答案共享的预算，而推理先生成。预算正常时推理会把它 吃光，答案返回空（finish_reason: length）— 我们见到 planner 悄悄返回 0 步。修复：thinking 开启时后端在调用方预算之上额外加推理余量。
  • ReAct × thinking 不兼容。V4 要求每轮多轮工具调用都回传上一轮的 reasoning_content，而 LangChain 的 agent 客户端不做这件事（第二轮 HTTP 400）。所以 ReAct 只跑 thinking-off — 这本身是个发现：推理模型与 agent 工具链之间存在成熟度落差。
这些是在全量评测之前用 token 用量诊断脚本抓到的，而不是事后 — 正是那种会悄悄毁掉整片实验格子的失败（"非思考"列其实在思考、空计划被当成 差答案打分），不查就会让数据作废。

5.2 懒加载单例的多线程竞态

HF 首次部署时报错 AttributeError: 'NoneType' object has no attribute 'encode'， 在 ReAct agent 并行调用多个工具时触发。 根因：LangGraph 把 tool 调用派发到线程池；_load_store() 懒加载 函数不是线程安全的。三个线程同时调用 SentenceTransformer(...).to('cuda') 破坏了 PyTorch 内部 CUDA 状态，导致某些线程视角下 _embed_model 是 None。

修复：在所有懒加载路径 （retrieval_tool / stats_tool / classifier_tool）加 threading.Lock + 双检锁。

5.3 稳健的规划与工具 I/O

plan-then-execute 范式依赖 planner 输出可解析的 JSON。thinking 模式下的规划是 随机的，偶尔产出无法解析的计划 → 0 步 → "无证据"答案（320 行里有 1 行）。 工具原本返回裸 Python list，某些 OpenAI 兼容 API 在其为空时会拒收。

修复：共享 planner 在解析为空时重试一次（正常的行不受影响）； 工具改为返回 JSON 字符串（空结果带提示字符串），这样错误的 business_id 也不会让下一轮请求失败。

5.4 Agent 工具集精简

较小的模型偶尔会陷入循环或多余调用 classify_review。 务实修复：从 Agent 工具集移除 summarize_evidence 和 classify_review（检索结果本身已包含星级数据，无需再分类）。 最终 Agent 工具栈：search_global、 search_by_business、get_business_stats。

7. 核心结论

  • 检索 grounding 主导质量：无检索的 Direct LLM 只有 0.2/8，而 所有带检索的系统都达到 7.8–8.0/8。决定领域问答质量的是 grounding， 而不是推理结构或模型尺寸。
  • 推理范式的选择是效率问题，不是质量问题：ReAct、Plan-and-Solve、 ReWOO、Reflection 在 DeepSeek-V4 上都达到天花板质量（≈8/8），区别只在成本和 延迟。Plan-and-Solve 和 ReWOO 最精简；ReAct 最贵（每轮重发历史）。见第 3 节。
  • thinking 税真实存在且没有回报：DeepSeek-V4 thinking 模式多花 ~3–4× 延迟、~2× 成本却没有可测的质量增益；显式 Reflection 也只是加成本、并不优于更简单的范式。质量饱和后，内部或外部的"额外 思考"在这里都不划算。
  • 后端抽象层确实回本：单方法的 BaseBackend 接口让我们 只用约 30 行就接入了 DeepSeek-V4，并把 320 条答案的研究和在线 demo 都指向它， 应用层代码一行未动。
